Архитектура LAIM

Путь AEF-трейса через систему: контракт данных, стадии s1–s4, узел laim-detector в режимах train и inference, узел LAIM RCA, где LLM отфильтровывает ложные срабатывания, и узел отчёта. Схемы соответствуют коду ветки claude/audit-05-fixes, коммит 283eb7b.

Карта

Сквозная схема

На схеме четыре запуска. Узел laim-detector в режиме train обучает детектор и собирает пакет модели. Тот же узел в режиме inference получает пакет через model_in и оценивает новые трейсы. Узел LAIM RCA проверяет каждое срабатывание с помощью LLM, узел LAIM anomaly report формирует HTML-отчёт. Блоки детектора, выровненные по вертикали, выполняют один и тот же код: при обучении он оценивает параметры, при инференсе применяет их.

s1 · ars/stages/s1__data.py · ars/data

Подготовка данных: от спанов к последовательностям

Класс аномалии определяется хешем trace_id с seed запуска и составом спанов трейса, поэтому план разбиения известен ещё до расчёта признаков. Благодаря этому отбор признаков и нормализация используют только нормальные трейсы TRAIN, хотя сами аномалии внедряются позже, в пространстве признаков и эмбеддингов. Числовая дорожка (EPI) и текстовая (SEM) сходятся в одну строку на пару (trace_id, agent_id).

Контракт данных (ars/specification/spec.py, ТЗ v1.9.2): 46 полей в 11 группах — id (6), время (2), статус (2), классификация (2), текст (2), LLM (11), HTTP (5), Kafka (4), LangGraph (7), сервис (3), meta (2). NULL запрещён: неприменимые значения кодируются сентинелами (-1, -1.0, false, '', root, outside, NONE, STATUS_CODE_UNSET). Обязательны 13 полей: все идентификаторы, оба времени, aef_kind, input_text, output_text и два логических поля сессии. Одно невалидное обязательное поле исключает весь трейс. Проверка (validation_gate) выполняется в laim/pipeline.py перед s1 и только для обучающих спанов: strict оставляет валидные трейсы в train_spans_validated.parquet, warn только записывает нарушения в журнал.

Классы внедряемых аномалий (ars/data/anomalies_injection.py). Класс присваивается, только если в трейсе есть спаны-мишени в ячейке (aef_kind, agent_id) размером не меньше 64 спанов; для hallucination достаточно llm-спана. Трейсы с меткой, но без изменённых спанов исключаются из VAL и TEST; счётчики по классам — injection_coverage в S1Meta, манифесте и eval_report.

s2 · ars/stages/s2__detector.py · ars/models/m2__detector

Детектор: два LSTM-автоэнкодера и автоэнкодер латентных векторов

Ветви обучаются по очереди: EPI-AE, SEM-AE, затем FMLP-AE на зафиксированных нормализованных латентных векторах. Метку аномалии ставит только ошибка FMLP-AE (e_comb) при сравнении с порогом. Ошибки ветвей в метке не участвуют, но входят в калибровку p_anomaly, поэтому у помеченного трейса возможно p_anomaly < 0,5.

Сетка экспериментов (ars/configuration/experiments/e2__detector.py). По умолчанию запускаются два кода из CODES. detector.experiments принимает любой код формата {epi}_{sem}_{comb}_{batch}_{lr}[_{arch}]; некорректный код вызывает ошибку до начала s1. Порог подбирается по detector.threshold_metric (по умолчанию youden), если эксперимент не задаёт метрику явно; эксперимент выбирается по select_metric на VAL. В S2Meta сохраняются selection_value (VAL) и test_value (TEST).

hub_mse_hub_32_4_deepdeep: 10 и 14 слоёв LSTM, FMLP-AE из 14 скрытых слоёвHuber / MSE / Huber321e-4

s3 · ars/stages/s3__classifier.py · ars/models/m3__classifier

Классификатор типа аномалии

Стекинг-ансамбль на JAX, обучение с учителем. Он обучается на внедрённых аномалиях из VAL ∪ TEST, а на инференсе размечает только помеченные трейсы внутри build_product_contract. Класса «норма» нет: ложному срабатыванию детектора тоже будет присвоен один из пяти типов. Ложные срабатывания отфильтровывает узел RCA.

s4 · m2__detector/attribution.py · ars/stages/s4__rca.py

Атрибуция ошибки реконструкции

Поэлементная ошибка ветви вычисляется в её функции потерь. Среднее по признакам даёт ошибку спана, среднее по валидным шагам — ошибку признака. Для каждого трейса результат хранится в индексном JSON rca_attribution. Для помеченных трейсов export_detector_rca добавляет имена, каталог спанов и значения в исходных единицах — блок laim.detector_rca/1.

Блок detector_rca: структура, а не пример значений (s4__rca.py)

// только для строк с detector_is_anomaly; строгий JSON без NaN
{ "schema": "laim.detector_rca/1", "agent_id",
  "scores": { p_anomaly, reconstruction_error // = e_comb
            , threshold
            , branch_z:   { behavior, semantic }  // robust z
            , flag_share: { behavior, semantic }  // comb_share_epi
            , logit:      { behavior, semantic, combined, bias } },
  "sequence": { spans, scored, truncated },
  "spans": { // только упомянутые, без сентинелов
    "<span_id>": { name, kind, status, status_message,
      parent_span_id, llm_model, llm_total_tokens,
      http_method, http_path, http_status_code,
      kafka_topic, graph_node, service, start_time,
      duration_s, input_excerpt, output_excerpt } }, // ≤ 200 симв.
  "feature_info": { "<feature>": { base, aggregation,
                   window, log1p, scope // step | sequence } },
  "behavior": {
    spans:    [ { rank, index, span_id, error, error_share,
                  vs_typical, drivers: [ { feature, direction,
                  observed, expected, observed_raw,
                  expected_raw, clipped, error } ] } ],
    features: [ { rank, feature, direction, observed, expected,
                  observed_raw, expected_raw, clipped, error,
                  error_share, vs_typical,
                  peak_span_index, peak_span_id } ] },
  "semantic": { spans: [ { rank, index, span_id, error,
                          error_share, vs_typical } ] } }

Как вычисляются значения. observed и expected = z · scale + shift, то есть значения в шкале самого признака (для лог-признаков — после log1p). *_raw обращает log1p только там, где это корректно (max, min, mean, квантили); для std и sum исходных значений нет. clipped ставится, если |z| достиг ограничения norm_z_clip (20). vs_typical — ошибка, делённая на медиану ошибки нормальных обучающих трейсов.

Похожие имена. Колонки detector_z_epi и detector_z_sem в detections.parquet — нормализованные латентные векторы (128 и 768), вход s3. Robust z-оценки ошибок есть только внутри rca_attribution и detector_rca (branch_z).

rca/ · отдельный узел SberDS · main.py::main

Узел RCA: проверка срабатывания и анализ первопричины

Узел не импортирует ars и laim; с детектором его связывает только JSON test_anomalies. Сигнал детектора (detector_rca) и связи между трейсами строятся детерминированно, без LLM. Отчёт о разработке агента, если подан, становится главным контекстом промпта. LLM возвращает вердикт и краткое описание первопричины без категорий; записи с вердиктом normal исключаются как ложные срабатывания.

Запись на входе (test_anomalies): 11 полей в фиксированном порядке и detector_rca

{ "anomalies": [ {
  _comment, trace_id, starttime, endtime,
  anomaly_type,          // из s3, пусто при ошибке
  confidence,            // round(p_anomaly · 100)
  business_description,
  user_query,            // первый input_request
  agent_response,        // последний output_request
  tech_details,          // узел RCA не заполняет
  rca_results,           // "" — заполняет узел RCA
  detector_rca           // только для помеченных
} ] }

Запись на выходе (res): та же запись без detector_rca; поля детектора не меняются, rca_results становится объектом

rca_results: {
  verdict: anomaly | uncertain | unverified,
  verdict_confidence, severity,
  rca: "Суть с фактами и trace_id. Возможные
        причины: 1) …; 2) …; 3) …"  // ≤ 600 символов
       // без LLM: { root_cause, evidence[],
       //            recommendation }
  location: { agent_id, span_id, span_name,
              span_kind, source: llm | detector },
  related_traces: [ trace_id, … ],  // упомянутые в rca
  detector_evidence: { p_anomaly, strength, signal,
    category, hypothesis, top_spans[≤3],
    top_features[≤4], caveats },
  analyzed_by: "llm:<model>" | "detector",
  agent_report_used: true }         // если отчёт дошёл до LLM

anomaly_report/ · отдельный узел SberDS · main.py::main

Узел отчёта: HTML-отчёт по аномалиям

Узел принимает res узла RCA (или непосредственно test_anomalies детектора) и формирует самодостаточный HTML без JavaScript и JSON-сводку со светофором. Используется только стандартная библиотека Python.

ШагЧто происходит
Фильтростаются записи с confidence ≥ min_confidence (по умолчанию 75). Детектор записывает туда round(p_anomaly · 100), узел RCA это поле не меняет, поэтому в отчёт попадают трейсы с p_anomaly ≥ 0,75. Записи дрифт-тестов и деградации качества исключаются, остальные сортируются по confidence
Типыanomaly_types = auto: блоки о типах показываются, только если s3 заполнил anomaly_type хотя бы у одной записи; show и hide включают и выключают их принудительно
HTML«Описание показателей» (типы и шкала confidence), «Сводка», «Перечень аномалий»: карточки с trace_id, временем, типом, confidence, запросом, ответом и RCA. trace_id в тексте RCA становятся ссылками на карточки; категории и служебные метки удаляются
Светофорamber, если показана хотя бы одна аномалия, иначе green; отдельного порога по числу аномалий нет

Выходные порты: anomaly_report — HTML на панели «Отчёт по аномалиям», all_results — сводка

all_results: {
  total, unique_traces, types, by_type[],
  shown, min_confidence,
  anomaly_types_shown, shown_by_type[],
  color: amber | green,
  test_name: "anomaly_report",
  calculated_traffic_lights: {
    test_light, semaphore_title } }

Запуск: локально и на SberDS

Локально все команды выполняются через run.py и laim.pipeline. На платформе дескриптор вызывает run.py::main → laim.platform.run_node, который преобразует порты и параметры формы в ту же конфигурацию. ars/main.py — устаревший адаптер; из него используются только Anomalies и extract_query_response.

Команды run.py. Конфигурация: TOML и --set section.key=value. Неизвестный ключ, некорректный код эксперимента, метрика или план внедрения вызывают ошибку до создания каталога прогона.
